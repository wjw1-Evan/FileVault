# FileVault 产品需求文档（PRD）

版本：v1.0 · 日期：2026-11-14 · 状态：已确认实施

## 1. 背景与痛点

- **Time Machine 粒度太粗**：系统备份以小时级快照为单位，恢复单个文件要进「时光机」界面翻找，且备份盘故障时历史全丢。
- **Git 对普通人门槛太高**：init/add/commit/push 一套概念和命令把非技术用户挡在门外；但 git 恰恰是最可靠的文件历史管理工具。
- **普通用户的 Mac 上没有 git**：macOS 默认不带 git，运行 git 会触发 Xcode CLT 安装（约 1.5GB），普通人无法完成。
- **文件只有单机一份**：重要文档、笔记、设计稿散落各处，没有顺手的远程备份手段。

## 2. 产品定位

**给普通人的文件时光机 — 基于 Git 的 macOS 菜单栏自动版本管理工具。**

常驻菜单栏，零操作把**你添加的每个文件夹**变成一个自动管理的版本仓库（v4.0 起不再按一级子文件夹拆仓）：变动自动提交、可绑定远程仓库自动上云、误删误改随时回滚。用户不需要知道 git 的存在。

## 3. 目标用户与画像

### 画像 A：写作者「小林」（主用户）

- 高校研究生，同时写论文和公众号；目录 `~/Documents/写作` 下有「论文」「公众号」「读书笔记」等子文件夹。
- 不会用命令行，机器上没装 git。
- 痛点：凌晨改稿误删一整章，Time Machine 快照不在身边，欲哭无泪。

### 画像 B：多设备知识工作者「小马」

- 笔记库 `~/Notes` 下按主题分几十个子文件夹，公司和家里两台 Mac。
- 痛点：两台设备间靠网盘同步，经常出现「conflicted copy」冲突文件。

## 4. 用户故事

1. 小林第一次打开 FileVault，不知道什么是 git，应用自动检测并准备好了 Git 环境，全程没见过终端。
2. 小林添加「写作」文件夹后，整个文件夹悄悄成了一个仓库——论文、公众号、根目录下的散落文件全都有版本历史，她毫无感知。
3. 小林连续打字一小时，期间保存 40 次，只形成几次合理的提交，而不是 40 条噪音历史。
4. 小林凌晨误删一整章，打开「恢复文件」，在「已删除」里一键找回昨晚那个版本，3 步内完成。
5. 小马给「写作」文件夹绑定了 GitHub 私有仓库并开启自动推送，每次提交后自动上云。
6. 小马在家改完笔记自动提交并推送，到公司另一台 Mac 上拉取即得最新版，不再用网盘传文件。
7. 断网时小马照常写作，提交照常进行；恢复网络后自动补推成功。
8. 小林做大批量整理时点了「暂停」，整理完点「恢复」，期间不产生噪音提交，恢复时补一次全量提交。
9. 设计软件生成 500MB 临时大文件，FileVault 自动排除，仓库没有膨胀。
10. 菜单栏图标时刻告诉小林：所有文件夹都安全（✓）、有待推送（↑）、或出了问题（⚠）。

## 5. 功能需求（P0/P1/P2）

### P0 — MVP 必须

| 编号 | 功能 | 说明 |
|---|---|---|
| FR-01 | **Git 环境检测与自动安装** | 首次启动检测 git；缺失时按「内嵌 git → Xcode CLT / Homebrew」顺序自动准备，过程 UI 可见、禁止静默失败，用户全程无需终端 |
| FR-02 | 根目录管理 | 添加/移除受管根目录，配置持久化 |
| FR-03 | 整个文件夹一个仓库 | 受管文件夹本身 `git init`（v4.0：不再拆一级子文件夹）；根目录散落文件、多级子文件夹、隐藏目录（除 `.git`/忽略规则）全部纳入；文件夹已有 `.git` 原样接管 |
| FR-04 | 变动监控与自动提交 | FSEvents 监控整个受管文件夹；任意文件变动后防抖 5s（最大等待 60s）自动 add+commit；防抖窗口内多次保存合并为 1 次提交；新建的空文件夹写入隐藏 `.gitkeep` 使其可被 Git 记录（Git 不跟踪空目录），提交信息为 `auto: 新建文件夹 X` |
| FR-05 | 自动提交信息 | `auto: N 处变更 (+X -Y)，新增 a.md，修改 b.txt，删除 c.log`（文件名最多列 5 个） |
| FR-06 | **远程仓库配置** | 每个受保护文件夹（= 一个仓库）配置远程地址（SSH/HTTPS），可为空=仅本地；remote 写入仓库自身 `.git/config`，与终端互通 |
| FR-07 | auto-push 与同步状态 | 提交成功后若开启自动推送则后台串行推送；状态机：无远程/已同步/待推送/推送中/失败；本地提交永远先行，push 失败不影响本地版本管理 |
| FR-08 | 菜单栏常驻与状态 | 菜单栏常驻；图标反映整体状态；菜单展示每个文件夹状态 |
| FR-09 | 历史时间线 | 查看每个受保护文件夹的提交历史（哈希/时间/提交信息）；版本内文件可预览（文本/图片内联，PDF 等其他二进制用默认应用打开）；详情区可切换「变更 / 全部」，**全部**展示该版本完整文件树（含未改动文件，可展开、预览、打开与恢复） |
| FR-10 | 文件恢复（v4.1 重新设计） | 「恢复」= ① 找回被删除的文件 ② 把改过的文件还原到以前的版本。独立「恢复文件」窗口按**文件**组织（不是按提交）：已删除 / 最近修改 / 全部 三个作用域，单文件的版本时间线可预览、与当前对比、用默认应用打开、恢复到任一版本（产生新提交，不动历史）；恢复前自动保存未提交改动。整仓（= 整个受保护文件夹）回滚保留在历史窗口（需确认；仅回退本地当前分支，远程仓库不改写；忽略规则排除的文件、大文件与嵌套仓库不受影响） |
| FR-11 | 忽略规则 | 自动注入 .gitignore 模板；大文件改写入 `.git/info/exclude`（不污染仓库） |
| FR-12 | 大文件保护 | 单文件上限跟随远端（github.com → 100MB，其他远端不设限）；超限文件自动排除并记录 |
| FR-13 | 暂停/恢复 | 全局/每根目录暂停自动提交，恢复时补一次全量检查 |

## 6. 非功能需求

| 可靠性 | 本地提交永远先行；push 失败不影响本地版本管理；0 数据损坏事故 |
| 验证 | 全部核心功能有自动化测试覆盖；`--smoke` 自检通过 |

| 兼容 | macOS 14+；iCloud/网盘目录可用但提示事件重复风险 |

## 6.5 明确排除项

- 不做网盘同步（非 Dropbox/坚果云类产品）
- 不做磁盘加密
- 不接管用户已有仓库的日常操作（受管文件夹本身已有 .git 时仅原样复用，不动配置；文件夹内部的嵌套 .git 目录不做特殊处理）
- 拉取时自动变基合并分叉：把本地未推送的自动提交重放到远程之上（不产生合并提交）；冲突则立即中止 rebase、恢复原状并列出冲突文件，绝不把冲突标记交给自动提交（v4.1.2，取代原「不自动 merge / 拉取向导」约定）
- 自动推送被拒（远程已有新提交）时自动补救：先按拉取规则快进/变基，再重试推送；同名文件冲突则中止 rebase、保留本地提交、通知用户并停止定时重试（不强推、不丢本地历史）（v4.1.5）
- 更换远程仓库：先解除旧远程的 upstream 与 refs/remotes/origin/*，再指向新远程并探测其内容；新远程为空 → 自动推送本地历史并重新绑定 upstream；新远程已有历史 → 若可快进（任一方是另一方祖先）自动继续，真正分叉/无关时才标记待决策并提示用户选择「同步（保留本地文件）」「强制拉取（以远程为准）」或「立即推送」，任一显式操作成功后解除（v4.1.6/4.1.7）
- 文件夹重定位：受保护文件夹被移动/改名，或外置盘挂载到新路径后，可在「更多 → 重新定位（文件夹被移动/改名）…」选择新位置；FileVaultService.relocateRoot 停掉旧 watcher、解除旧路径、挂载新路径并把配置里的 root 路径改为新路径（保留 paused），仓库 .git 随文件夹移动因此历史/远程绑定不丢；目标已在受保护列表时报错不改动任何状态（v4.2.5）
- 自动保存兜底：除 FSEvents 事件驱动提交外，每约 2 分钟做一次安全巡检（sweepOnce）：遍历未暂停的受保护文件夹，发现未提交改动就补提交，避免休眠唤醒/事件丢失导致改动长期未入库；暂停的文件夹跳过（v4.2.4）
- 后台静默与通知节流：所有 git 调用禁用交互式凭证/SSH 提示（GIT_TERMINAL_PROMPT=0、ssh BatchMode+ConnectTimeout），缺凭证/密钥时立即失败并给出可读的修复指引，不会在后台挂起或弹窗；推送失败重试期间只通知一次（首次失败），最终放弃时再通知一次并说明重试次数（v4.2.3）
- 全自动同步兜底：自动推送被远程新提交拒绝、而快进/变基又遇到同名文件冲突或历史完全不相关时，自动改用「保留本地文件」的无损合并（远程版本另存为「远程副本」）后重推，不再只发通知等用户去终端；自动提交失败（磁盘空间不足、无写入权限、index.lock 占用、所有者不一致）用可读原因通知，并自动重试最多 3 次（新文件改动会重新计数），避免改动一直未入库（v4.2.2）
- **v4.2 产品方向**：远程只保留「自动同步」——移除立即推送/拉取远程更新/强制拉取/同步远程文件到本地四个手动入口与「提交后自动推送」开关；保存地址即开启同步；绑定或更换一个已有内容的远程时自动做无损合并（远程独有文件进来、本地文件保留、同名不同内容保留两份「远程副本」）随后自动推送；升级时旧的「自动推送关闭」配置自动转为开启。v4.2.1：自动信任受保护文件夹（命令级 safe.directory，适配外置盘/其他账户的 dubious ownership）；多个远程时可在「更多 → 同步使用的远程」里选择，写入 branch.<分支>.remote/merge 后自动同步即走该远程
- 系统环境容错：Git 报 dubious ownership（文件夹属于其他账户/外置盘）时给出 safe.directory 命令；多个远程且无上游时列出远程名并提示设置上游；崩溃留下的过期 .git/index.lock（>5 分钟）可在「修复未完成的合并/变基…」中一并清理（v4.1.9）
- 文件不丢边界：被忽略的本地文件（.DS_Store 等）与远程新增文件同名时，拉取/强制拉取/同步会先把本地内容另存为「name (本地副本).ext」再继续，避免 git 静默覆盖；崩溃/强退留下的半完成合并/变基提供「修复未完成的合并/变基…」一键清理（只丢中间状态，不丢已提交历史与文件）（v4.1.8）
- 远程兼容与容错：绑定远程时补默认 fetch refspec；分支名不一致（本地 main / 远程 master）时列出远程实际分支并给出 set-upstream 命令；分支保护、仓库规则、pre-receive hook、文件过大等远程拒绝可读化且只通知一次、停止重试；index.lock 占用给出清理指引；fetch/pull/push 超时放宽到 120 秒并转为可读超时提示（v4.1.7）
- 历史互不相关（例如新建仓库绑定了已有历史的远程）不做自动合并，提供两个手动出口：
  - 「同步远程文件到本地（保留本地文件）」：无损同步——远程独有文件下载到本地，本地独有文件保留，同名不同内容保留两份（本地版本沿用原名，远程版本另存为「名称 (远程副本)」）；合并前备份旧 HEAD，合并生成提交后自动把本地领先的提交推送上去，让两边保持一致（v4.1.4）
  - 「强制拉取（以远程为准）」：先把旧 HEAD 备份到 refs/filevault/backup，再 fetch + reset --hard 到远程分支，并绑定上游（v4.1.2）

## 7. 成功指标

- 新用户从安装到首次自动提交 ≤ 3 分钟（含 git 自动准备）

- 每周活跃用户中开启远程备份的比例 > 30%
- 0 起数据丢失事故

## 9.5 FR-20 自动更新（v1.1.0 新增）

- 检查：启动后 20s 静默检查 + 菜单手动触发；数据源 `gh api repos/…/releases/latest`
- 比较：语义化版本（tag 去 v 前缀）
- 安装：`gh release download` → sha256 与资产 digest 比对 → ditto 解压 → 旧 bundle 转 `.old` → 新 bundle 就位 → `open` 重启
- 呈现（v3.1.7 起）：**不弹窗**——检查/下载（百分比+字节）/校验/安装/重启各阶段以一行文字显示在菜单栏菜单里；手动检查的结果（已是最新/失败原因）同样写在菜单里
- 测试：9 项（版本比较表/解析/校验拒绝/替换仿真）+ 真实仓库端到端验证
- 路线：用户量扩大后迁移 Sparkle（EdDSA 签名 + appcast）
