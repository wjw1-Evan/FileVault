# FileVault 产品需求文档（PRD）

版本：v1.0 · 日期：2026-11-14 · 状态：已确认实施

## 1. 背景与痛点

- **Time Machine 粒度太粗**：系统备份以小时级快照为单位，恢复单个文件要进「时光机」界面翻找，且备份盘故障时历史全丢。
- **Git 对普通人门槛太高**：init/add/commit/push 一套概念和命令把非技术用户挡在门外；但 git 恰恰是最可靠的文件历史管理工具。
- **普通用户的 Mac 上没有 git**：macOS 默认不带 git，运行 git 会触发 Xcode CLT 安装（约 1.5GB），普通人无法完成。
- **文件只有单机一份**：重要文档、笔记、设计稿散落各处，没有顺手的远程备份手段。

## 2. 产品定位

**给普通人的文件时光机 — 基于 Git 的 macOS 菜单栏自动版本管理工具。**

常驻菜单栏，零操作把**你添加的每个文件夹**变成一个自动管理的版本仓库（v4.0 起不再按一级子文件夹拆仓）：变动自动提交、可绑定远程仓库自动上云、误删误改随时回滚。用户不需要知道 git 的存在。

## 3. 目标用户与画像

### 画像 A：写作者「小林」（主用户）

- 高校研究生，同时写论文和公众号；目录 `~/Documents/写作` 下有「论文」「公众号」「读书笔记」等子文件夹。
- 不会用命令行，机器上没装 git。
- 痛点：凌晨改稿误删一整章，Time Machine 快照不在身边，欲哭无泪。

### 画像 B：多设备知识工作者「小马」

- 笔记库 `~/Notes` 下按主题分几十个子文件夹，公司和家里两台 Mac。
- 痛点：两台设备间靠网盘同步，经常出现「conflicted copy」冲突文件。

## 4. 用户故事

1. 小林第一次打开 FileVault，不知道什么是 git，应用自动检测并准备好了 Git 环境，全程没见过终端。
2. 小林添加「写作」文件夹后，整个文件夹悄悄成了一个仓库——论文、公众号、根目录下的散落文件全都有版本历史，她毫无感知。
3. 小林连续打字一小时，期间保存 40 次，只形成几次合理的提交，而不是 40 条噪音历史。
4. 小林凌晨误删一整章，打开「恢复文件」，在「已删除」里一键找回昨晚那个版本，3 步内完成。
5. 小马给「写作」文件夹绑定了 GitHub 私有仓库，之后每次提交都自动上云（v4.2 起保存远程即开启同步）。
6. 小马在家改完笔记自动提交并推送，到公司另一台 Mac 上拉取即得最新版，不再用网盘传文件。
7. 断网时小马照常写作，提交照常进行；恢复网络后自动补推成功。
8. 小林搬运外置盘时把那个文件夹单独暂停，搬完恢复，期间不产生噪音提交，恢复时补一次提交；应用整体没有关闭自动提交的开关（v4.2.22）。
9. 设计软件生成 500MB 临时大文件，FileVault 自动排除，仓库没有膨胀。
10. 菜单栏图标时刻告诉小林：所有文件夹都安全（✓）、有待推送（↑）、或出了问题（⚠）。

## 5. 功能需求（P0/P1/P2）

### P0 — MVP 必须

| 编号 | 功能 | 说明 |
|---|---|---|
| FR-01 | **Git 环境检测与自动安装** | 首次启动检测 git；缺失时按「内嵌 git → Xcode CLT / Homebrew」顺序自动准备，过程 UI 可见、禁止静默失败，用户全程无需终端 |
| FR-02 | 根目录管理 | 添加/移除受管根目录，配置持久化 |
| FR-03 | 整个文件夹一个仓库 | 受管文件夹本身 `git init`（v4.0：不再拆一级子文件夹）；根目录散落文件、多级子文件夹、隐藏目录（除 `.git`/忽略规则）全部纳入；文件夹已有 `.git` 原样接管 |
| FR-04 | 变动监控与自动提交 | FSEvents 监控整个受管文件夹；任意文件变动后防抖 5s（最大等待 60s）自动 add+commit；防抖窗口内多次保存合并为 1 次提交；新建的空文件夹写入隐藏 `.gitkeep` 使其可被 Git 记录（Git 不跟踪空目录），提交信息为 `auto: 新建文件夹 X` |
| FR-05 | 自动提交信息 | `auto: N 处变更 (+X -Y)，新增 a.md，修改 b.txt，删除 c.log`（文件名最多列 5 个） |
| FR-06 | **远程仓库配置** | 每个受保护文件夹（= 一个仓库）配置远程地址（SSH/HTTPS），可为空=仅本地；remote 写入仓库自身 `.git/config`，与终端互通 |
| FR-07 | auto-push 与同步状态 | 提交成功后后台串行推送（v4.2 起自动推送恒开，无开关）；状态机：无远程/已同步/待推送/推送中/失败；本地提交永远先行，push 失败不影响本地版本管理 |
| FR-08 | 菜单栏常驻与状态 | 菜单栏常驻；图标反映整体状态；菜单展示每个文件夹状态 |
| FR-09 | 历史时间线 | 查看每个受保护文件夹的提交历史（哈希/时间/提交信息）；版本内文件可预览（文本/图片内联，PDF 等其他二进制用默认应用打开）；详情区可切换「变更 / 全部」，**全部**展示该版本完整文件树（含未改动文件，可展开、预览、打开与恢复） |
| FR-10 | 文件恢复（v4.1 重新设计） | 「恢复」= ① 找回被删除的文件 ② 把改过的文件还原到以前的版本。独立「恢复文件」窗口按**文件**组织（不是按提交）：已删除 / 最近修改 / 全部 三个作用域，单文件的版本时间线可预览、与当前对比、用默认应用打开、恢复到任一版本（产生新提交，不动历史）；恢复前自动保存未提交改动。整仓（= 整个受保护文件夹）回滚保留在历史窗口（需确认；仅回退本地当前分支，远程仓库不改写；忽略规则排除的文件、大文件与嵌套仓库不受影响） |
| FR-11 | 忽略规则 | 自动注入 .gitignore 模板；大文件改写入 `.git/info/exclude`（不污染仓库） |
| FR-12 | 大文件保护 | 单文件上限跟随远端（github.com → 100MB，其他远端不设限）；超限文件自动排除并记录 |
| FR-13 | 暂停/恢复 | 每根目录暂停自动提交（v4.2.22 移除全局暂停：自动提交始终开启、不可关闭）；恢复时补一次检查 |

## 6. 非功能需求

| 维度 | 指标 |
|---|---|
| 性能 | 空闲 CPU < 1%，常驻内存 < 80MB |
| 提交聚合 | 防抖窗口内多次保存合并为 1 次提交；遗漏事件可自愈（提交前用 git status 兜底） |
| 可靠性 | 本地提交永远先行；push 失败不影响本地版本管理；0 数据损坏事故 |
| 验证 | 全部核心功能有自动化测试覆盖；`--smoke` 自检通过 |
| 隐私安全 | 凭证只存 macOS 钥匙串；配置明文可审计（JSON）；本地优先，无云端中转 |
| 兼容 | macOS 14+；iCloud/网盘目录可用但提示事件重复风险 |

## 6.5 明确排除项

- 不做网盘同步（非 Dropbox/坚果云类产品）
- 不做磁盘加密
- 不接管用户已有仓库的日常操作（受管文件夹本身已有 .git 时仅原样复用，不动配置；文件夹内部的嵌套 .git 目录不做特殊处理）
- 拉取时自动变基合并分叉：把本地未推送的自动提交重放到远程之上（不产生合并提交）；冲突则立即中止 rebase、恢复原状并列出冲突文件，绝不把冲突标记交给自动提交（v4.1.2，取代原「不自动 merge / 拉取向导」约定）
- 自动推送被拒（远程已有新提交）时自动补救：先按拉取规则快进/变基，再重试推送；若同名文件冲突或历史互不相关，则自动改用「保留本地文件」的无损合并（远程版本另存为「远程副本」）后重推（v4.1.5 起先中止 rebase 通知用户，v4.2.2 起改为全自动）；不强推、不丢本地历史
- 更换远程仓库：先解除旧远程的 upstream 与 refs/remotes/origin/*，再指向新远程并探测其内容；新远程为空 → 自动推送本地历史并重新绑定 upstream；新远程已有历史 → 若可快进（任一方是另一方祖先）自动继续，真正分叉/无关时自动做无损合并后推送（v4.1.6/4.1.7 曾要求用户三选一，v4.2 起全自动）
- 自动提交始终开启（v4.2.22）：移除菜单里的「自动提交已开启」开关与全局暂停 API（PauseController.isGloballyPaused/setGlobalPaused、FileVaultService.setGlobalPaused、AppState.paused/toggleGlobalPause）；菜单不再有暂停入口，主面板与菜单栏图标不再有“已暂停”状态；单文件夹暂停保留（设置 → 文件夹 → 更多 → 暂停自动提交），用于搬运外置盘等局部场景
- 设置卡片状态去重（v4.2.21）：文件夹卡片标题行的状态图标与展开区状态图标重复，改为标题行保留图标、展开区只显示一行状态文字（已同步/待推送/仅本地…）+ 健康信息，避免“两个一样的状态图标”
- 历史与恢复合并窗口（v4.2.20）：原「历史版本」与「恢复文件」两个独立窗口合并为 RecordsWindow 的两个标签页（找回与还原 / 历史时间线），两者常驻同一窗口以保留各自选中的文件夹与版本；菜单入口合并为「历史与恢复…」，AppState.open("history"/"recovery") 映射到该窗口并定位到对应标签；--render-history/--render-recovery 调试渲染同步更新
- 操作精简（v4.2.19）：菜单栏去掉与自动提交语义重复的「立即提交」、去掉与标题图标重复的「打开主面板」；主面板去掉与活动卡重复的「查看历史版本」；设置里每个文件夹的认证方式（自动/令牌/SSH）默认折叠为一行摘要，仅需要时展开，默认视图只剩「远程地址 + 保存 + 测试 + 状态」
- 一步添加文件夹：首次启动、菜单栏与主面板的「添加文件夹…」共用同一个添加窗口（QuickAddSheet）：选择文件夹即完成保护；若文件夹已有 git 远程地址自动检测并预填，也可同窗口粘贴远程地址一起绑定（绑定失败保留已添加状态并提示），或留空以后再在设置里绑定。首启不再先跳设置页，减少「设置→添加→远程→保存」多步操作（v4.2.18）
- 定时双向同步：安全巡检每 remoteSyncInterval（默认 300 秒，启动时首次立即执行）检查每个有远程且未暂停的文件夹——有远程新提交就自动拉取（快进/自动变基；同名冲突或无关历史用无损合并保留双方），本地领先则自动推送；失败静默留给推送循环/认证巡检报告，不打扰用户（v4.2.17）
- 回滚不误删未纳管文件：整个文件夹回滚到一个“该文件夹不存在”的版本时，先扫描文件夹内未跟踪/被忽略的文件（如 .env、构建产物）；若存在则拒绝回滚并列出前 3 个文件名，提示先移走或纳入版本管理，绝不静默删除（v4.2.16）
- 启动补交：应用启动、挂载完受保护文件夹后立即执行一次安全巡检（sweepOnce），把上次退出前 5 秒防抖尚未触发、或退出瞬间写入的改动补提交，避免“改了但没关够久所以没保存”；暂停文件夹仍跳过（v4.2.15）
- 恢复边界：找回被删除的深层文件时自动重建被一起删掉的父文件夹；若目标路径当前是一个文件夹（用户把文件换成了同名目录），恢复前先给出可读错误「请先改名或移走」且绝不覆盖目录；目标版本里该路径是目录而非文件时按「版本里没有这个文件」处理（v4.2.14）
- 云盘目录提示：受保护文件夹位于 iCloud Drive（Mobile Documents/com~apple~CloudDocs）、Dropbox、OneDrive、Google Drive 等云盘目录时，设置页健康信息追加「☁️ <provider> 目录（按需下载可能被误判为删除）」；因为在线占位符文件在 git 看来像被删除，提前告知用户改用本地文件夹或关闭按需下载（v4.2.13）
- 只读/归档远程拒绝：推送被托管平台以「只读、已归档、无写权限」拒绝时归类为确定性失败，只通知一次并提示去调整仓库状态，而不是反复重试（v4.2.13）
- 配置自恢复：ConfigStore 每次保存前把上一份可正常解码的 config.json 复制为 config.backup.json；读取时主文件损坏则回退备份并置 lastLoadIssue=recoveredFromBackup，两者都不可读则 lastLoadIssue=unreadable；FileVaultService 启动时据此通知用户（已从备份恢复 / 以空列表启动但磁盘仓库未删除），下次保存会用缓存重写 config.json，损坏主文件另存为 config.corrupt-时间戳.json 供排查（v4.2.12）
- 提交说明健壮性：自动提交说明里的文件名会去掉换行/制表符等控制字符并截断到 60 字符，新文件夹标记名也如此，保证提交标题始终单行、不会被超长或特殊文件名破坏（v4.2.11）
- 特殊文件名健壮性：git status / ls-files / diff --name-only / 树差异统计一律使用 -z（NUL 分隔）解析，文件名含空格、换行、引号或「->」时不会被 C 引号转义或被误拆分；重命名即使新名字里含「->」也能正确取到原路径（v4.2.10）
- 多实例互斥：每个受保护文件夹在 .git 下维护 filevault-instance.pid；启动/挂载时若发现另一个仍存活的实例持有锁，本实例跳过监听（设置页显示「另一个 FileVault 实例正在管理（pid N）」），避免两个实例重复提交/推送；持有者退出后，安全巡检会自动接管；崩溃留下的陈旧锁（pid 不存在）会被直接接管（v4.2.9）
- 不可用与空历史可见性：受保护文件夹不存在（外置盘未挂载/被移走）或不再是 Git 仓库时，RepoHealth.available=false，设置页健康信息显示「⚠️ 文件夹当前不可用（可能未挂载或被移动）」；启动时若已配置的 root 丢了 .git 且文件夹非空，attachRoot 会在重新初始化后发通知，说明「已重新初始化为空历史，如之前推送过远程请重新填写远程地址」（首次添加普通文件夹不误报）（v4.2.8）
- 监听自愈与首推超时：安全巡检除了补提交，还会检查监听状态——外置盘掉线重连、FSEvents 流停止后自动重新挂载监听；推送单次超时（默认 120 秒）但第一次尝试就超时时，自动用 5 倍预算（600 秒）重试一次，避免大文件夹首次推送反复失败（v4.2.7）
- 大文件排除可见性：超过远端单文件上限的文件会自动写入 .git/info/exclude 并排除提交，但必须让用户知道「它没有被备份」——CommitEngine.onLargeFilesExcluded 首次排除时发通知（文件名 + 说明），RepoManager.excludedLargeFiles 解析 exclude 规则计数，RepoHealth 在设置页健康信息里显示「⚠️ N 个大文件未同步」（v4.2.6）
- 文件夹重定位：受保护文件夹被移动/改名，或外置盘挂载到新路径后，可在「更多 → 重新定位（文件夹被移动/改名）…」选择新位置；FileVaultService.relocateRoot 停掉旧 watcher、解除旧路径、挂载新路径并把配置里的 root 路径改为新路径（保留 paused），仓库 .git 随文件夹移动因此历史/远程绑定不丢；目标已在受保护列表时报错不改动任何状态（v4.2.5）
- 自动保存兜底：除 FSEvents 事件驱动提交外，每约 2 分钟做一次安全巡检（sweepOnce）：遍历未暂停的受保护文件夹，发现未提交改动就补提交，避免休眠唤醒/事件丢失导致改动长期未入库；暂停的文件夹跳过（v4.2.4）
- 后台静默与通知节流：所有 git 调用禁用交互式凭证/SSH 提示（GIT_TERMINAL_PROMPT=0、ssh BatchMode+ConnectTimeout），缺凭证/密钥时立即失败并给出可读的修复指引，不会在后台挂起或弹窗；推送失败重试期间只通知一次（首次失败），最终放弃时再通知一次并说明重试次数（v4.2.3）
- 全自动同步兜底：自动推送被远程新提交拒绝、而快进/变基又遇到同名文件冲突或历史完全不相关时，自动改用「保留本地文件」的无损合并（远程版本另存为「远程副本」）后重推，不再只发通知等用户去终端；自动提交失败（磁盘空间不足、无写入权限、index.lock 占用、所有者不一致）用可读原因通知，并自动重试最多 3 次（新文件改动会重新计数），避免改动一直未入库（v4.2.2）
- **v4.2 产品方向**：远程只保留「自动同步」——移除立即推送/拉取远程更新/强制拉取/同步远程文件到本地四个手动入口与「提交后自动推送」开关；保存地址即开启同步；绑定或更换一个已有内容的远程时自动做无损合并（远程独有文件进来、本地文件保留、同名不同内容保留两份「远程副本」）随后自动推送；升级时旧的「自动推送关闭」配置自动转为开启。v4.2.1：自动信任受保护文件夹（命令级 safe.directory，适配外置盘/其他账户的 dubious ownership）；多个远程时可在「更多 → 同步使用的远程」里选择，写入 branch.<分支>.remote/merge 后自动同步即走该远程
- 系统环境容错：Git 报 dubious ownership（文件夹属于其他账户/外置盘）时给出 safe.directory 命令；多个远程且无上游时列出远程名并提示设置上游；崩溃留下的过期 .git/index.lock（>5 分钟）可在「修复未完成的合并/变基…」中一并清理（v4.1.9）
- 文件不丢边界：被忽略的本地文件（.DS_Store 等）与远程新增文件同名时，拉取/合并/重置前会先把本地内容另存为「name (本地副本).ext」再继续，避免 git 静默覆盖；崩溃/强退留下的半完成合并/变基提供「修复未完成的合并/变基…」一键清理（只丢中间状态，不丢已提交历史与文件）（v4.1.8）
- 远程兼容与容错：绑定远程时补默认 fetch refspec；分支名不一致（本地 main / 远程 master）时列出远程实际分支并给出 set-upstream 命令；分支保护、仓库规则、pre-receive hook、文件过大等远程拒绝可读化且只通知一次、停止重试；index.lock 占用给出清理指引；fetch/pull/push 超时放宽到 120 秒并转为可读超时提示（v4.1.7）
- 历史互不相关（例如新建仓库绑定了已有历史的远程）：
  - v4.2 起**全自动**：绑定/更换一个已有内容的远程时，用无损合并（保留本地版本到原名、远程版本另存为「名称 (远程副本)」、允许 unrelated histories）生成合并提交，随后自动推送，用户不需要做任何选择（v4.1.4 的「同步（保留本地文件）」由界面手动触发，v4.2 起并入自动流程）
  - 内部仍保留「强制拉取（以远程为准）」实现（先把旧 HEAD 备份到 refs/filevault/backup，再 fetch + reset --hard 并绑定上游），用于测试与内部兜底；v4.2 界面不再提供手动入口（v4.1.2）
