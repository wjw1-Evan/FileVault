# 0003 · 恢复/回滚与同步共用两级锁 + 忽略文件护栏

- 状态：已采纳（v4.2.26）
- 日期：2026-11-16
- 证据：`Sources/FileVaultCore/RepoManager.swift:43`（本地锁）、`RepoManager.swift:66`（远程锁）、`RepoManager.swift:776-778`（恢复按「远程→本地」取锁）、`Sources/FileVaultCore/CommitEngine.swift`（自动提交只 tryAcquire 本地锁）

## 背景

恢复/回滚直接改写工作区与 index，而自动提交、后台拉取/变基也在同一仓库上跑。旧代码只有「远程操作互斥」一把锁，恢复不参与，导致 index.lock 冲突、checkout 已生效但 commit 失败、rebase 中 reset 留下半合并状态；同时 `reset --hard` / checkout 会静默覆盖被忽略文件。

## 选项

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 只加超时重试 | 改动小 | 半提交/覆盖风险仍在，无法证明安全 |
| 两级锁 + 护栏（新） | 本地改写与远程操作互斥；忽略文件有交集检查 | 所有恢复入口必须按同一顺序取锁，改动面较大 |

## 决定

- 锁顺序固定为「先 remoteOp、后 localOp」；自动提交只 tryAcquire localOp（拿不到就跳过，等下一轮）；拉取/合并/恢复都取两把锁。
- 任何 reset/checkout 前先算「目标提交树 ∩ 当前 ignored/untracked」，命中即抛可读错误，绝不静默覆盖。

## 后果

- 好的：恢复与自动提交/同步不再交错；被忽略的 .env 等文件不会被回滚吞掉。
- 坏的：恢复期间自动提交最多延后一轮；实现必须保持锁顺序，否则可能死锁。
- 后续：新增任何「改写工作区」的功能（批量恢复、清理等）必须复用这两级锁与交集检查。
