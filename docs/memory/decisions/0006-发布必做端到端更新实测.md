# 0006 · 发布零用户可见行为改动也要走完整端到端更新实测

- 状态：已采纳（v4.2.33 起沿用）
- 日期：2026-11-21
- 证据：v4.2.33 发布记录（README「下载安装」段、docs/11 §7）、`README.md:69`

## 背景

v4.2.33 只改了菜单弹层的绘制与配色，不碰任何数据、同步、更新逻辑。这类「纯 UI 轮」很容易被当成低风险，打包后直接发版——而实际上发布包本身（`make_app.sh` 的 plist、内嵌 git、签名）和自动更新链（资产命名、bundle id、sha256）恰恰是纯 UI 轮最容易漏测的部分：UI 改动不会被 `swift test` 覆盖，单测全绿也证明不了装得上。

## 决定

**每次发布（含纯 UI 轮）都必须做一次真实的「上一版 → 新版」端到端自动更新实测**，用 `FV_CONFIG_DIR` 隔离配置，绝不能碰用户真实配置。

流程（`scripts/make_app.sh <版本>` → zip → 哈希 → Release 之后）：

1. 解包上一版 zip 到 `/tmp` 沙盒，`FV_CONFIG_DIR=/tmp/...` 启动它；
2. 等它自己走完 检查 → 下载 → sha256 校验 → 原子替换 → 重启；
3. 断言：`Info.plist` 版本变成新版、旧包变成 `Pastward.app.old` 且版本仍是上一版、两端 bundle id 相同、更新后的安装 `--smoke` 通过；
4. 清理沙盒，确认无残留进程。

## 后果

- 好的：把「装得上」与「测得绿」两件事都钉住了；v4.2.33 借此确认更新链在纯 UI 轮后依然完好。
- 代价：每次发布多约 2 分钟与一次 22 MB 下载。
- 注意：ad-hoc 签名（本机无 Developer ID 证书）下 `spctl` 必然 `rejected`，这是预期状态，`codesign --verify` 通过即可；对外分发仍需 `CODESIGN_IDENTITY` + 公证，流程见 README「打包分发」。
