# 项目记忆

记忆存放在当前仓库的 `docs/memory/`，规则以 `docs/memory/README.md` 为准。本技能规定**何时读、何时写、写成什么样**。

## 一、开工前：按需检索，别全读

1. 判断任务是否需要历史：涉及“为什么这么设计 / 以前怎么处理的 / 有没有注意事项”才需要。
2. 用关键词检索，而不是通读：

   `grep -rn "关键词" docs/memory/`

3. 先看 `docs/memory/README.md` 的索引，再打开命中的条目。
4. 记忆与代码冲突时**以代码和 git 历史为准**，并顺手修正记忆 —— 不要把过时结论当事实执行。

不需要历史的任务（改个文案、跑个测试）直接跳过，不要为了走流程而读。

## 二、收工时：只写值得写的

满足任一条件才写：

| 类型 | 判据 | 写到哪里 |
| --- | --- | --- |
| 决策 | 两种做法都可行，选择理由不在代码里 | `docs/memory/decisions/NNNN-短标题.md` |
| 坑 | 根因不直观、下次还可能踩 | `docs/memory/gotchas.md` |
| 约定 | 命名、目录、错误文案、流程 | 对应章节或 `AGENTS.md` |

以下**不写**：

- 过程流水账（“先试了 A 失败，又试了 B”）
- 代码里读得出来的东西（函数签名、目录结构）
- 临时状态（今天的进度、待办）
- 密钥、令牌、个人信息、用户数据

## 三、写成什么样

一条记忆 = 标题（结论）+ 原因 + 证据 + 影响，控制在 10 行内：

`@
### 结论：一句话说清是什么（≤ 30 字）

- 原因：为什么这么做，取舍是什么
- 证据：`路径:行` / 提交哈希 / 日期
- 影响：什么情况下会再遇到，怎么规避
`@

- 证据必须可核验：能给 `文件:行` 就不写“某处”。
- 日期用 `YYYY-MM-DD`。
- 决策用 `decisions/TEMPLATE.md` 的骨架，编号顺延。

## 四、写完要收尾

1. 更新 `docs/memory/README.md` 的索引（新增条目必须出现在表里）。
2. 同一事实有旧条目时，**改写或删除旧的**，不要留两份互相矛盾的记忆。
3. 单文件超 200 行就按主题拆分。

## 五、反例

- ❌ “修复了 HistoryView 的崩溃问题” —— 没结论、没原因、没证据。
- ✅ “历史列表崩溃是 diff 缓存在主线程写造成” —— 结论 + 根因 + `HistoryView.swift` 证据。
- ❌ 把整个调试过程贴进 `gotchas.md` —— 下次没人读得完。
- ✅ 只留“现象 → 根因 → 规避方式”三句。
