# FileVault

**给普通人的文件时光机 — 基于 Git 的 macOS 菜单栏自动版本管理工具**

FileVault 常驻 macOS 菜单栏，对你添加的每个文件夹，**直接在该文件夹根上初始化一个 Git 仓库**（v4.0 起不再按一级子文件夹拆仓）；监控到文件变动后自动提交。核心价值：**零操作的文件历史版本管理**——误删误改随时找回，可选绑定远程仓库自动备份上云。

> ⚠️ 命名说明：FileVault 与 macOS 自带的磁盘加密功能同名，存在搜索混淆与审核风险，正式发布前建议评估改名（候选：Vaultkeeper / TimeGit / SnapKeep / Histodeck）。

## 核心功能

1. **零配置起步** — 首次启动自动检测 Git 环境；缺失时自动安装：**内嵌 git（零下载）→ 5 个下载镜像逐个尝试并 sha256 校验 → 最后才回退 Xcode CLT**，全程无需命令行。下载地址与实测速度见 [docs/07-Git自动安装与镜像源.md](docs/07-Git自动安装与镜像源.md)。
2. **整个文件夹一个仓库** — 添加一个文件夹，它本身就是一个 Git 仓库：根目录下的散落文件、多级子文件夹、隐藏目录（除 `.git` 与忽略规则外）全部纳入版本管理；文件夹本身已有 `.git` 则原样接管复用，绝不破坏（文件夹内部嵌套的 `.git` 属于用户自己的项目仓库，不递归接管）。
3. **自动版本管理** — FSEvents 监控文件变动，5 秒防抖聚合后自动 `add + commit`，提交信息自动总结变更（如 `auto: 3 处变更 (+120 -40)，新增 a.md，修改 b.md`）。 新建的空文件夹会放入一个隐藏的 `.gitkeep`（Git 不记录空目录），让文件夹本身也进入版本历史、回滚时可一并还原。
4. **远程仓库绑定** — 每个受保护文件夹可单独配置远程地址（GitHub/GitLab/Azure DevOps 等）与**身份验证**（自动 gh 凭证助手 / 用户名+访问令牌——选择后会出现两个输入框，点「保存」写入本机凭证库（优先钥匙串，不会写进 git 配置）/ SSH 密钥），开启「提交后自动推送」，本地优先、失败自动重试；**凭证过期/认证失败主动巡检提醒**（每 6 小时，去重不骚扰）；**Git 报「文件夹所有者与本机账户不一致」时给出 safe.directory 修复命令；多个远程无法确定上游时列出实际远程名并给出设置上游命令；崩溃残留的 .git/index.lock（超过 5 分钟）可在「修复未完成的合并/变基…」里一并清理（v4.1.9）**；**被忽略的本地文件（如 .DS_Store）在拉取/强制拉取/同步时若远程也新增了同名文件，会先另存为「本地副本」再拉取，不会被静默覆盖丢失**；**崩溃/强退残留的合并或变基可在「更多 → 修复未完成的合并/变基…」一键清理（不丢已提交历史与文件）**（v4.1.8）；**拉取/推送失败按类型给出可执行说明**：分支名不一致会列出远程实际分支并给出设置上游命令，分支保护/仓库规则/文件过大拒绝只通知一次并停止重试，`index.lock` 占用给出清理指引，网络命令超时放宽到 120 秒并转为可读提示（v4.1.7）；**更换远程仓库时会先清掉旧远程的跟踪分支与上游再指向新仓库**：新仓库是空的就直接把本地历史推上去；新仓库已有内容则不会自动合并/推送，而是提示你选「同步（保留本地文件）」「强制拉取（以远程为准）」或「立即推送」**（v4.1.6）**；**自动推送被远程新提交拒绝时（例如另一台机器刚推过），先自动快进/变基再重试，不会一直失败、也不会强推**；**「拉取远程更新」能快进就快进，两边都有新提交时自动变基合并（未提交改动先存成提交），冲突则立即中止并恢复原状、列出冲突文件**；**添加远程后两边都有文件时用「同步远程文件到本地（保留本地文件）」——远程独有的下载到本地、本地独有的原样保留、同名不同内容的两份都留（本地版本沿用原名、远程版本另存为「远程副本」），合并后自动推送让两边一致，文件不丢**（v4.1.4）；**历史完全对不上、只想要远程内容时可「强制拉取（以远程为准）」——先自动备份旧版本再覆盖本地**（v4.1.2；v4.1.1 起失败会说明原因并给出下一步）。
5. **菜单栏常驻** — 状态图标实时反映整体状态（空闲/同步中/待推送/异常）；菜单只保留一行摘要「N 个文件夹 · 正常」+ 每个受保护文件夹一行（状态点 + 状态词）+ 常用操作，详情都在主面板/设置里（v3.1.5 精简，不再堆砌健康度文字与版本号）。
6. **历史时间线** — 按天分组的提交时间线 + 本地搜索；选中任意版本可**预览其中文件**（文本与图片内联显示，PDF 等其他二进制用默认应用打开）。详情区可在「变更」与「全部」之间切换：**全部**展示该版本完整的文件树（含未改动的文件，可预览/打开/恢复），不再受“本次提交改了什么”限制。单个文件还能打开它自己的版本时间线（每行可直接恢复）、做任意两版本对比、看逐行差异与逐行归属（blame）；右上角菜单可导出该版本、给版本命名（标签）、恢复整个子目录，以及找回被回滚的版本。这里适合“看历史、回退整个文件夹”；按文件找回/还原请用下面的「文件恢复」窗口。
6.5 **快速打开** — 菜单栏与设置窗口均可一键在 Finder 中打开已添加的目录。
6.6 **主控面板** — 菜单「打开主面板」(⇧⌘D)：状态总览 + 跨仓库最近活动流 + 目录卡片；窗口按内容自适应，单屏完整显示无滚动条（v3.4.1）。
7. **文件恢复（v4.1 重新设计）** — 「恢复」只做两件事：**找回被删除的文件**、**把改过的文件还原到以前的版本**。菜单「恢复文件…」打开独立的恢复窗口，它按**文件**组织而不是按提交：左边自动列出**已删除**的文件和**最近修改**的文件（也可切到「全部」按文件名/路径搜索）；选中文件后，右边是它自己的版本时间线（日期 + 提交说明 + 短哈希），可预览当时内容、切到「与当前对比」看差异、用默认应用打开，或一键**恢复到此版本**。恢复只影响这一个文件：恢复前自动保存未提交改动，恢复本身也记成一个新版本（`restore: 找回/还原 …`），之后仍可再回退。**整个文件夹的回滚**作为破坏性操作留在历史窗口：仅回退本地当前分支，远程不变；忽略项、大文件与嵌套仓库保持原样；回滚前状态备份到隐藏 ref（`refs/filevault/backup`，可用 git 找回）。不存在的文件/版本会明确报错而不是静默失败（v3.3.1；恢复核心 40 项专门测试覆盖）。
8. **忽略规则** — 自动注入 .gitignore 模板（.DS_Store、node_modules 等），设置窗口内可视化编辑，改动会被自动提交。
9. **大文件保护** — 单文件上限**跟随远端**（无本地阈值设置）：github.com 远端自动按 100 MB 硬限制排除文件，其他远端不设限；设置页按仓库展示远端上限，避免仓库膨胀或推送必然失败。
10. **手动暂停** — 一键暂停/恢复自动提交，恢复时自动补一次全量提交。
11. **测试连接** — 配置远程后一键验证可达性与认证（`git ls-remote`），失败原因直接可读。
12. **仓库健康度** — 设置窗口展示每仓库提交数 / 体积 / 最近提交时间；超过 2GB 告警。
13. **每周自动 gc** — 仓库每周自动 `git gc --auto`，控制 .git 膨胀。
14. **SSH 密钥引导** — 配置 SSH 远程时检测 ~/.ssh 密钥，缺失时给出指引。
15. **失败系统通知** — 自动提交/推送失败时发送系统通知（本地提交永远先行，失败不影响本地版本管理）。
16. **中英双语界面** — 设置 → 语言 可切换「跟随系统 / 简体中文 / English」，默认匹配 macOS 语言；切换后自动重启应用生效（v3.4.0，含 200+ 条人工翻译与完整性测试）。

## 典型场景

| 场景 | FileVault 的价值 |
|---|---|
| 论文写作误删一整章 | 菜单「恢复文件…」→ 已删除里找到它 → 一键找回 |
| 设计稿改坏了想反悔 | 最近修改里选中文件，还原到改坏前的那个版本 |
| 一整批改动都不对 | 历史窗口把整个文件夹回滚到之前的提交 |
| 笔记库多机使用 | 每个受保护文件夹一个私有远程仓库，提交后自动推送，多机同步备份 |

## 系统要求

- macOS 14.0+
- Apple Silicon / Intel
- 无需预装 Git（应用会自动准备）

## 自动更新

应用内置更新器（FR-20）：启动 **20 秒后**静默检查一次 GitHub Releases，之后**每小时一次**；检查失败 **10 分钟**后重试（并显示失败状态）；设置里重新打开「自动检查更新」会立即恢复检查（v3.1.4），**发现新版本自动下载安装并重启**（受「自动检查更新」开关门控）。安装流程：字节级下载（实时百分比+字节数）→ sha256 校验 → **更新包签名/身份校验**（v3.3.0：校验 bundle id 与代码签名，正式签名版还会钉住 Team ID）→ 原子替换 bundle（旧版保留 `.old` 可回滚）→ 自动重启。**启动失败自动回退**（v3.3.0）：新版本连续 3 次未能正常启动时，自动换回上一版本并通知。仅 `.app` 包内运行时可用。

**进度只在菜单里看（v3.1.7）**：更新不再弹出任何窗口或对话框。打开菜单栏图标即可看到一行实时状态——`正在下载更新 42%… · 840 KB / 2 MB` → `正在校验更新…` → `正在安装更新…` → `更新完成，正在重启…`；手动「检查更新…」的结果也写在菜单里（如 `已是最新版本（v3.1.5）`、`更新失败：…`），不会打断你正在做的事。

## 打包分发

```bash
./scripts/vendor-git.sh --arch all   # 可选：预取内嵌 git（下载 + sha256 校验 + 剔除 GCM，见 docs/07）
./scripts/make_app.sh                # release 构建 + 组装 FileVault.app（含图标、内嵌 git、ad-hoc 签名）
hdiutil create -volname FileVault -srcfolder build/FileVault.app -format UDZO dist/FileVault.dmg
# 或（沙箱环境替代方案）：
ditto -c -k --keepParent build/FileVault.app dist/FileVault-1.0.0.zip
```

- 产物：`FileVault.app`（LSUIElement 菜单栏模式、bundle 通知可用、设置内可开启「登录时启动」）
- Release 实测：RSS 54–60MB、空闲 CPU **0.07%**（事件驱动刷新后，较轮询架构降低约 14 倍）、二进制 0.8MB
- 本地构建默认 ad-hoc 签名；**对外分发必须正式签名 + 公证**：
  `CODESIGN_IDENTITY="Developer ID Application: 你的名字 (TEAMID)" NOTARY_PROFILE=fv-notary ./scripts/make_app.sh 3.2.0`
  （公证需先执行一次 `xcrun notarytool store-credentials fv-notary --apple-id … --team-id … --password …`）

## 仓库卫生：GitHub 100 MiB 限制

GitHub 对普通 Git 仓库的单文件有 **100 MiB 硬限制**（50 MiB 起警告，超限直接拒绝 push）。本仓库约定：构建产物与发布包一律不进 Git，二进制分发只走 Releases。新克隆请执行一次：

```bash
./scripts/install-git-hooks.sh   # 启用 pre-commit 守卫（阻止 > 100 MiB 文件）
./scripts/check-large-files.sh   # 手动全历史体检
```

完整方案与应急处理：[GitHub 100 MB 文件限制解决方案](docs/05-GitHub-100MB限制解决方案.md)
